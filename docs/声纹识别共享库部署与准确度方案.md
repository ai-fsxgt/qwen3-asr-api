# 声纹识别共享库部署与准确度方案

**中文** | [English](声纹识别共享库部署与准确度方案_EN.md)

## 1. 最终架构

两个 ASR 服务连接同一个 PostgreSQL/pgvector 实例。登记、追加模板、改名、删除和
识别全部直接访问数据库，不维护进程内全量声纹缓存，所以任一服务写入后，另一个
服务下一次查询立即可见。

当前规模只有数百名说话人，识别使用 pgvector 精确余弦距离查询，不创建 HNSW
近似索引。这样不会因近似召回损失准确度；数据规模显著增长后再根据实测延迟决定
是否加索引。

## 2. 准备 PostgreSQL/pgvector

数据库镜像固定为：

```text
registry.cn-hangzhou.aliyuncs.com/ripper/pgvector:pg16
```

项目不再内置 PostgreSQL 编排。请由部署环境独立创建数据库，并确保 vLLM 容器能通过
内网地址连接；如果使用上述镜像，持久化 `/var/lib/postgresql/data`。端口 5432 只允许
ASR 服务器访问，不得向公网开放。

生产环境应同时做到：

- 修改默认密码，不把密码提交到仓库；
- 仅允许两台 ASR 服务器访问 5432，不向公网开放；
- 定期备份 `qwen3_asr` 数据库和数据库数据卷；
- 两个 ASR 服务设置完全相同的 `SPEAKER_DATABASE_URL`。
- 多实例部署必须保持 `speaker_store_audio: false`。当前的进程内锁无法协调不同实例，开启音频留存后可能在删除说话人时残留音频文件。

示例连接地址：

```bash
SPEAKER_DATABASE_URL='postgresql://qwen3_asr:强密码@数据库IP:5432/qwen3_asr'
```

数据库与 ASR 容器在同一台主机时，`数据库IP` 应填写容器可达的宿主机地址或把它们
接入同一 Docker 网络；不要在容器内填写 `127.0.0.1`。数据库位于独立服务器时填写
数据库服务器内网 IP。

## 3. ASR 配置

两个服务均设置：

```yaml
enable_speaker: true
enable_speaker_db: true
speaker_identify_min_sec: 5.0
speaker_realtime_confirmations: 2
speaker_id_threshold: 0.45
speaker_id_margin: 0.10
speaker_auto_enroll: false
speaker_store_audio: false
```

`api_key` 仍是声纹管理接口的硬性要求。数据库连接地址优先通过
`SPEAKER_DATABASE_URL` 环境变量传入，避免把密码写进 `config.yaml`。

## 4. 准确度保护规则

- 手动登记允许 1 条模板，不强制多条；接口在少于 3 条时返回质量建议。
- 实时识别按簇累计至少 5 秒有效语音后才查库。
- 实时连续两次命中同一身份后才展示姓名；连续两次 unknown 或其他身份会撤销或切换。
- 实时簇质心按语音时长加权，长而清晰的片段权重更高。
- 达到最大说话人数后，低于聚类阈值的片段保持匿名，不强制归给最近说话人。
- 离线簇不足 5 秒时保持匿名。
- `top1 < speaker_id_threshold` 或 `top1-top2 < speaker_id_margin` 时拒绝认人。
- 未知说话人默认不自动登记，防止把噪声、串音或错误聚类写入长期声纹库。
- 每次识别记录时长、top1、top2、margin 和拒绝原因，供后续基于真实数据标定阈值。

## 5. 旧 SQLite 数据的手工迁移

系统不会自动迁移，也不会在启动时读取旧 SQLite。迁移脚本默认只检查源库：

```bash
cd asr-service
venv/bin/python scripts/migrate_speaker_sqlite_to_postgres.py \
  --sqlite-path data/speakers.db
```

确认检查结果、完成数据库备份且目标库为空后，才可由管理员手工执行：

```bash
cd asr-service
SPEAKER_DATABASE_URL='postgresql://qwen3_asr:强密码@数据库IP:5432/qwen3_asr' \
  venv/bin/python scripts/migrate_speaker_sqlite_to_postgres.py \
  --sqlite-path data/speakers.db \
  --apply
```

脚本会锁定目标表，并在同一事务内完成空库检查、写入和四类记录数量校验；任何一步
失败都会回滚。脚本保留说话人 ID、模板 ID、认领幂等记录和审计记录。

## 6. 上线顺序

1. 启动 pgvector，确认健康检查通过。
2. 备份旧 `speakers.db`，先执行迁移脚本的只检查模式。
3. 如需旧数据，再由管理员安排维护窗口手工执行 `--apply`；不需要旧数据则直接从空库开始。
4. 先切换一个 ASR 服务并验证登记、识别、删除，再切换第二个服务。
5. 在任一服务新增一名测试说话人，确认另一服务无需同步即可识别。
6. 观察审计数据并制作同人/异人验证集，再调整阈值；不要凭单个样本直接改阈值。
